I don't start AI projects by choosing an LLM framework. I start by defining state, execution boundaries, deterministic paths, failure modes, and evaluation. Then I decide where an LLM actually belongs.

I spent 9 months as a full-stack developer at Symbiosis Systems, shipping 3 enterprise apps with ASP.NET and SQL Server. That experience shaped how I think about persistence, APIs, validation, and software that has to survive real usage.

Now I apply that discipline to multi-agent systems, RAG pipelines, tool execution, and cost-aware LLM workflows in Python — using frameworks as implementation tools, not as architecture.

$ openWaypoint

SHEET 01, IN PROGRESS

Multi-agent AI trip planner. You describe a trip through a structured form, a graph of LangGraph agents plans transport, lodging, activities, and budget, the system produces a day-by-day itinerary, and you refine it through a chat-based review loop before finalizing.

5 LangGraph agents7 mechanical tool nodesPostgres checkpointingHuman review + replanning
Engineering signal: state is explicit and write-safe; external tools are separated from agent reasoning; failures route through critique instead of disappearing inside a retry loop.
Build note
Why this architecture: Each tool node (flights, trains, hotels, activities) writes to a separate TypedDict key so parallel fan-out via LangGraph's Send API is write-safe. No merge conflicts. The Postgres checkpointer survives browser refresh and server restart. The human-review gate was added after early versions produced itineraries with impossible connections, like a red-eye flight followed by a 6am hotel check-in.
SpecDetail
AgentsConcierge to Planner to Budget to Itinerary to Critic. 5 LangGraph agents with human-in-the-loop review
Tools7 mechanical tool nodes: flights, trains, buses, cars, hotels, activities, weather. Staged dummy to free API to MCP
StateTypedDict TripState, separate keys per tool result for write-safe parallel fan-out. Postgres checkpointer survives refresh and restart
StackPython, LangGraph, FastAPI, Postgres, SQLAlchemy, Pydantic, Groq, Tavily

$ openhArILIVE

SHEET 02, DEPLOYED

RAG document intelligence. Upload PDFs or CSVs, ask questions, get cited answers. Rebuilt from a single-store ChromaDB prototype into a hybrid-search, multi-user system.

hybrid vector + full-textmulti-user scoped retrievalcited answersDuckDB SQL isolation
Engineering signal: the architecture changed in response to real failure modes , shared retrieval scope, exact-match misses, and unsafe CSV execution.
Live demo sleeps after 12 hours of inactivity (Streamlit Cloud). First load may take 30 to 60 seconds to wake up.
Build note
Why the migration: The ChromaDB prototype struggled with multi-user document isolation. Every user queried the same collection. I migrated to Supabase + pgvector for per-user scoping via Row Level Security. The hybrid retrieval (vector + full-text) was added after pure semantic search kept missing exact keyword matches in legal and financial documents. DuckDB replaced pandas.exec() after I realized untrusted CSV queries could execute arbitrary Python.
SpecDetail
RetrievalHybrid: pgvector similarity + tsvector full-text via a custom Supabase RPC
CSV queriesDuckDB SQL engine replacing pandas.exec() for safe multi-CSV queries
UsersSupabase Auth, per-user chat persistence, citation UI with telemetry feedback

$ openAI Agent Engine

SHEET 03, SHIPPED

Autonomous agent engine. A 4-layer pipeline routes ~80% of queries with 0 LLM calls and keeps measured per-session cost around ~$0.0005.

~80% zero-LLM routes~$0.0005 / session~30ms retrieval benchmarkReplanning on failure
Five sequential agents handle planning, validation, execution, replanning on failure, and response.

Engineering signal: deterministic routing is treated as a first-class execution path, with LLM calls reserved for cases that actually need inference.
Build note
Why this design: I built this after watching API costs scale linearly on a previous project. The cache layer came first. The pattern router came after I noticed about 40% of remaining queries were deterministic (greetings, status checks, timezone conversions). The daily quota enforcement was a hard lesson. A runaway overnight job burned through an entire API quota before morning. The Replanner agent was added when the Executor started failing silently on edge cases instead of retrying with a different approach.
SpecDetail
Retrieval layerChromaDB + SentenceTransformer RAG, ~30ms latency (measured on 200-query benchmark set)
Cost controlToken tracking and daily quota enforcement
PipelinePlanner to Validator to Executor to Replanner (on failure) to Responder. Auto-retry with replanning
TraceabilityEvery decision logged at session level for full audit trail
StackPython, LangChain, ChromaDB, Gemini, FastAPI, Pydantic
github.com/harshbhanushali26/ai-agent-engine

$ openFinOS

SHEET 04, SHIPPED

Full-stack AI finance platform. A dashboard for passive logging plus a conversational agent for active querying, both writing to the same SQLite store. Third generation of the system.

Build note
Why three generations: The first version stored everything in JSON files and had no query layer. The second added SQLite but every query hit the LLM, which was slow and expensive. This version introduces pattern matching for ~60% of queries (balance checks, category sums, monthly averages) so they resolve with 0 LLM calls. Complex queries stream via Groq with Server-Sent Events. The financial health score was the hardest part. It took four iterations to weight the factors in a way that matched how people actually think about their money.
SpecDetail
Query routing~60% of queries answered by pattern matching, 0 LLM calls. Complex queries stream via Groq + SSE
FeaturesFinancial health scoring, spending forecasts, budget threshold alerts
Authbcrypt-hardened auth with session tokens and CLI-based recovery
StackPython, FastAPI, SQLModel, Groq, SSE
